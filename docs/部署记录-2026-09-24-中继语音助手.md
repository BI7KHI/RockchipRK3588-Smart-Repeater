## 1. 架构位置

`nau8822` 采集设备**独占**，全板只有一路 `arecord`。助手作为采集中枢的
**第三个消费者**挂上去，与语音日志、APRS TNC 共用同一份 16 kHz 立体声块：

```
app.py::_mic_capture_loop  (唯一 arecord)
  ├─ voice_service.feed()      语音日志：BUSY/PTT 触发录音 + 归档
  ├─ aprs_service.feed()       APRS：常驻 Bell202 TNC
  └─ assistant_service.feed()  ← 本模块：唤醒 + 回答
```

之所以不能再开第二路 `arecord`：设备独占，第二路直接 `Device or resource busy`。

## 2. 语音识别路线 / ASR route

### 2.1 三层结构

| 层 | 职责 | 实现 |
|---|---|---|
| 采集层 | 单路采集，多消费者分发 | `_mic_capture_loop` → 三个 `feed()` |
| **识别层** | **唯一识别入口** | `voice_service.transcribe_pcm()` |
| 应用层 | 归档 / 唤醒 / 发射 | `voice_service` / `assistant_service` |

`transcribe_pcm()` 内部固定顺序：

```
去直流 + 250 Hz 高通 + 峰值归一化  (enhance_for_asr)
        ↓
silero VAD 切分  (min_speech 0.25 s / min_silence 0.25 s)
        ↓
merge_segments 合并  (gap 0.45 s / pad 0.15 s / 单段 ≤12 s)
        ↓
SenseVoice int8 逐段识别  (sherpa-onnx, threads=4)
```

**为什么必须共用这一个入口**：曾一度让语音日志与助手各写一套预处理/VAD/合并
逻辑，同一条空口录音（`voice_logs #92`）两处识别结果不同——语音日志得到
`中继台现在风速多少？`，助手得到`一台现在风速多少？`，开头两个音节被吃掉。
抽成唯一入口后两边结果一致（有 `deploy/test_shared_asr.py` 回归守着）。

### 2.2 关键决策与依据

| 决策 | 备选方案 | 实测依据 |
|---|---|---|
| 助手**自带轻量分段**，不直接订阅语音日志的 ASR 结果 | 挂 `vlog` 转录回调 | 归档 `vlog_post_roll=2.0 s` 才收段，唤醒会白等 2 秒 |
| 与语音日志**共用 `transcribe_pcm`** | 各写一套 | 同一条录音两处结果不同（见 2.1） |
| **保留 `asr_language=auto`** | 强制 `zh` | 4 组对照实验（auto/zh × 原始/预处理）**全部 1/5 命中**，`auto` 无劣势 → 不改动既有约束 |
| 起判门限 **-50 / -56 dBFS** | -40 / -46 | 空闲噪声底中位 **-68.9**（20 样本，-72.4~-65.5）；接收语音最弱 **-42.1**。取两者之间：离噪声底 15.5 dB、离最弱语音 8 dB |
| 前置缓冲 **1200 ms** | 400 ms | 反推取音窗口：助手起点比语音起点晚约 0.65 s（「中」是低能量声母），400 ms 补不回来 |
| VAD **不做自行边界裁剪** | 裁 50 ms 余量 | silero 报出的首段起点比真实语音起点晚约 320 ms，自裁会剪掉「中继」 |

### 2.3 实测基线（全部来自本板真实数据）

| 指标 | 实测值 | 说明 |
|---|---|---|
| 空闲噪声底 | **-68.9 dBFS** | 20 次采样，范围 -72.4 ~ -65.5，很稳 |
| 接收语音电平 | 中位 **-24.9**，最弱 **-42.1** dBFS | 26 段历史记录 |
| 自发发射电平 | 中位 -13.5 dBFS | 比接收响，但被 PTT 门控排除 |
| 音频质量 | 削顶 0、峰均比 11.7~17.1 dB、低频 <250 Hz 仅 0.3~0.6% | 语音带占比 86~96% |
| ASR 耗时 | **120~170 ms**（5~6 s 音频） | RTF ≈ 0.03~0.04 |
| LLM 耗时 | **3.9~6.8 s** | 含 2 轮工具调用 |
| TTS 耗时 | **1.2~1.5 s** | Piper 中英混读 |
| 单次发射 | **3.3~5.4 s** | 回复 15~26 字 |
| 松手→出声 | **约 8 s** | 收段 0.45 + ASR 0.15 + LLM 4.5 + TTS 1.4 + 起 PTT 0.12 |

## 3. 发射安全

助手是**自动发射**、无人值守，因此下列红线是硬约束，不因任何理由放宽：

| 保护 | 默认 | 行为 |
|---|---|---|
| 单次发射上限 | 30 s | 到点 `kill` aplay 并松 PTT |
| 两次发射最短间隔 | 15 s | 不足则等待，超预算放弃本次回答 |
| BUSY 等待上限 | 8 s | 信道一直忙就放弃，**绝不硬插** |
| 发射余波保护 | 600 ms | 发射后这段时间不收音，防自激 |
| 禁发时段 | 可配 | 如 `23:00-07:00`，跨零点正确解析 |
| 手动测试 | 无条件不发射 | 页面「跑一轮（不发射）」优先级高于一切设置 |
| 一键停止 | — | 立即打断播放、清空待处理队列、关闭追问窗口 |

**工具白名单**：助手只允许调用 `action=false` 的**只读**工具。
`agent_service` 里的 `speak` 是 `action=true`（会直接压 PTT 发射），若被模型调用会
**绕过上述全部安全线**，因此被显式排除，且 `ctx` 里连引用都不保留。

## 4. 现场缺陷与修复（全部有实测依据）

### 4.1 首发成功后永久失聪 ← 最严重

**现象**：首发成功，随后连续三次呼叫（语音日志全部收到且识别正确）助手一段都没收到，
`counters.segments` 停在 1。

**根因**：发射余波保护写成

```python
self.tx_until = max(self.tx_until, ts + guard)   # 保护期内的每个采集块都执行
```

它是「当前时刻 + 0.6 s」，而保护期内每个采集块（64 ms）都会执行一次，
于是截止时间被无限往后推，**保护期永不结束**。

**修法**：保护期改从「**最后一次观测到 PTT 有效**」起算（`tx_last_ts`）。
回归测试：`deploy/test_assistant_logic.py` 第 7 节，连跑 3 轮
「发射→静默→呼叫」都必须能收音。

### 4.2 唤醒词开头被剪掉

「中继台」被识别成「一台」。用 5.625 s（助手实际段长）窗口在真实录音上滑动反推，
确认助手取音窗口起点比语音起点晚约 0.27 s。根因是自行给 VAD 只留 50 ms 头部余量，
而 silero 的首段起点本身晚约 320 ms。**修法**：不再自裁边界，改走共用入口 + 前置缓冲提到 1.2 s。

### 4.3 手动测试按钮真的发射了

页面写着「不发射」，实现却只读设置项，而设置项默认允许发射——首次实测占用信道 5.44 s。
**修法**：`no_tx=True` 无条件拦截，优先级高于一切设置。

### 4.4 LLM 回显提示词

`_build_prompt` 已拼好「系统设定+历史+问题」，`_ask` 又把它当作用户问题包了一层，
第二轮总结取前 100 字正好截在「【系统设定】」开头，1.5B 模型直接照抄。
**修法**：`ask_fn` 区分 `prompt`（第一轮）与 `question`（总结轮）。
同时 LLM 耗时从 18.2 s 降到 3.9 s。

### 4.5 状态机永远停在「未启用」

启用后若一直没人讲话，没有任何代码把 `stage` 从初始的 `off` 推进到 `idle`。
**修法**：空闲分支补 `_set_state('idle')`。

### 4.6 LLM 保活从未生效

`voice_service.llm_start()` 返回 **bool**，返回 `(ok, msg)` 元组的是
`VoiceService.ensure_llm_ready()`。按元组解包每次都抛
`TypeError: cannot unpack non-iterable bool object` 并被 except 吞掉。
后果：每次唤醒都要等 20~40 秒冷启动。**修法**：按 bool 解包。

## 5. 工程陷阱（与业务无关，但都真实踩过）

| 陷阱 | 后果 | 对策 |
|---|---|---|
| `init_db()` 用 `INSERT OR IGNORE` 播种默认值 | **改代码里的 DEFAULTS 对已装环境无效**，数据库里的旧值一直赢 | 每改一个默认值都配一个迁移脚本，只在库里仍等于旧默认值时才覆盖 |
| bash heredoc 吃反斜杠 | 正则 `\1` 落盘变成 `\x01` 控制字符，反向引用彻底失效 | 凡带转义的文件一律用直传方式写，不走 heredoc |
| Python `Path.write_text()` 在 Windows 转 CRLF | 6 个文件被静默改成 CRLF | 统一用 `write_bytes()` + 显式替换 |
| 批量替换误伤同名变量 | `api_agent_chat` 里被替成未定义的 `q_short`，网页 Agent 对话抛 `NameError` | 替换后按「所在函数」自检变量可见性 |

## 6. 网页界面

独立页面 `/assistant`（导航栏「中继语音助手」），六个区块：

- **实时状态机**：监听 / 有人讲话 / 识别中 / 思考中 / 合成中 / 等信道 / 发射中 / 余波保护 / 追问窗口
- **实时电平波形**：约 20 秒输入电平 + 起判门限参考线
- **实况识别流**：含**未命中唤醒词**的原文，用于调唤醒词与判断灵敏度
- **对话记录**：双方原文/回复、发射时长、各阶段耗时、是否截断、可回放双方音频
- **设置区**：唤醒词、交互形态、分段灵敏度、发射红线、LLM 预算、提示词、音色，全部在线可改即生效
- **提示词与清洗**：逐字预览「运行前实际注入的提示词」，以及 Piper 朗读前的 Markdown/emoji 清洗效果

另有 `GET /api/assist/debug`：**识别音频留档环**（最近 12 条，含未命中的）。
这项是踩了 4.2 之后补的——出问题能直接听助手到底收到了什么，不必再反推。

## 7. 已知限制

- `asr_language` 与语音日志共用，无法为助手单独设定（引擎切换语言会重载模型，代价不可接受）
- 唤醒词为字面 + 同音字集合匹配（`中继→中继记纪计技济机基…`），非拼音级匹配
- 追问窗口内**任意**语音都会当作问题，噪声段可能触发一次无意义回答
- 无多轮指代消解评测，`assist_history_turns=6` 为经验值
- 保持 LLM 常驻占约 2.3 GB，可用内存从 2.7 GB 降至约 0.5 GB
- 未实现「唤醒词 + APRS 文本消息」入口

## 9. 复现步骤

```bash

scp board/deploy/test_shared_asr.py elf@<board>:/tmp/ && ssh elf@<board> 'python3 /tmp/test_shared_asr.py'
```
