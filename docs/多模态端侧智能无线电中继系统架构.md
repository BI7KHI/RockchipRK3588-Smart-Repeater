# 多模态端侧智能无线电中继系统架构（2×GM3188 + 第三方控制板 + ELF2/RK3588）

> 适用对象：项目前期总体方案设计、接口选型、软件模块划分与可实施路线。
> 硬件基础：Motorola GM3188 ×2（RX + TX）+ 第三方中继控制板 + Forlinx ELF2(RK3588) 开发板。
> 射频架构：不使用双工器，采用双天线架构。
> 文档基于本地 `ELF2` 开发资料（快速使用手册、硬件设计教程、原理图、引脚复用表）与互联网公开资料整理。

---

## 1. 系统目标与总体判断

本系统希望把“模拟 FM 中继/中转电台”升级成一个可被 AI 控制、可远程监控、可组网、可语音交互的端侧智能节点：

- 接收设备：Motorola GM3188 #1（RX），只负责接收；提供 BUSY/COS、SPK/DF 音频等扩展接口。
- 发射设备：Motorola GM3188 #2（TX），只负责发射；提供 PTT、MIC 输入、频率选择等扩展接口。
- 射频架构：**不使用双工器，采用双天线架构**。RX 天线接 GM3188 #1，TX 天线接 GM3188 #2；依靠异频、收发天线空间隔离与必要滤波抑制干扰。
- 中转/信号接口：第三方中继控制板，将两台 GM3188 的音频、BUSY、PTT、频率选择等信号整理成便于外部控制器使用的接口，引出 `DF、SPK、BUSY、PTT、MIC、GND、VCC、PC0-3`。
- 智能主控：ELF2(RK3588)，负责音频采集/输出、GPIO 频率与 PTT 控制、ADC 电压采集、RS485 气象数据采集、端侧 LLM/TTS/ASR 推理、Web/API、FRP 公网访问、VOIP/组网桥接。

**总体判断：**
1. 这套系统**可实现**。两台 GM3188 分别作为接收机和发射机，即典型的“双机异频中继”方案：接收机收到下行信号 → 控制板/ELF2 做解调、判断和语音处理 → 发射机在上行频率转发或播报。由于不使用双工器，需保证 RX/TX 频差足够，并将两根天线在空间上分开架设，必要时增加 RX 带通滤波器或 TX 带阻/带通滤波，防止发射机阻塞接收机。
2. ELF2/RK3588 拥有 8 核 CPU、6 TOPS NPU、NAU88C22 音频 Codec、标准 3.5mm 音频座、40Pin/20Pin GPIO、UART、ADC、千兆网/Type-C 等资源，适合做“中继控制器 + 边缘 AI 盒子 + VoIP 网关”三合一。
3. 端侧 LLM 建议从 **Qwen2.5 1.5B/3B 级别 Int4** 起步；端侧 TTS 建议 **Piper / sherpa-onnx 中文模型**；关键“时间、气象、点名”等指令应走**确定性快捷链路**，不依赖大模型，满足即时性。

## 2. 硬件接口与电气设计

### 2.1 RX GM3188 / TX GM3188 / 第三方控制板与 ELF2 的信号关系

实际部署为两台 GM3188：

- **GM3188 #1 = RX 接收机**：天线接 RX 频率，BUSY/COS 表示收到信号，DF/SPK 提供接收音频，供 RK3588 录音/识别/转发。
- **GM3188 #2 = TX 发射机**：天线接 TX 频率，由 RK3588/控制板控制 PTT，并将 MIC 输入接到 ELF2 的音频输出或 RX 转发音频，从而完成异频中继或智能播报。
- 第三方中继控制板建议只做“电平转换、隔离、音频缓冲、PTT 驱动、双机互锁”，**不承载智能逻辑**；所有智能逻辑放在 RK3588。

> 注意：若第三方控制板只有一组 `PTT/MIC/BUSY/DF/SPK` 对外接口，需要确认它内部已经完成“RX 音频→TX MIC”“BUSY→PTT”的中继接线；RK3588 则在“智能插入/播报/远端转发”时接管或叠加控制。若控制板支持双 GM3188 连接，最好按 RX/TX 分开接入 ELF2，以便 AI 分别获取接收状态和独立控制发射。

| 信号 | 所在电台 | 方向 | ELF2/RK3588 建议接入 | 说明 |
|---|---|---|---|---|
| DF（鉴别/解调音频） | RX GM3188 | RX→ELF2 | 音频输入（经衰减/隔离后到 3.5mm MIC 或 Codec Line-in） | 作为中继/语音识别主音频源 |
| SPK（扬声器音频） | RX GM3188 | RX→ELF2 | 音频输入监测/录音（经衰减网络） | 若 DF 不易引出，可用 SPK 经衰减；功率电平高，严禁直连 |
| BUSY / COS | RX GM3188 | RX→ELF2 | GPIO 输入（光耦隔离，3.3V 兼容） | 判断是否有下行载波/静噪打开 |
| RX 频率/信道选择 | RX GM3188 | ELF2→RX | PC0-3 或其他 GPIO → 光耦/电平转换 | 切换接收频率/信道；编码以控制板手册为准 |
| PTT | TX GM3188 | ELF2→TX | GPIO 输出 → 光耦/三极管 → 控制板 PTT | 控制发射机；必须低电平有效或按控制板定义；需防误触发 |
| MIC | TX GM3188 | ELF2→TX | ELF2 3.5mm 耳机/喇叭输出 → 衰减到 MIC 电平 → TX MIC | 智能播报、TTS、VOIP 语音、转发语音均走此路径 |
| TX 频率/信道选择 | TX GM3188 | ELF2→TX | PC0-3 或其他 GPIO → 光耦/电平转换 | 切换发射频率/信道；若 RX/TX 频率需要联动，由软件统一写 |
| GND | RX/TX 公共地 | - | 单点共地，音频建议隔离地 | 防止地环路和 RF 干扰 |
| VCC | 控制板供电 | - | 建议独立 12V/5V，RK3588 GPIO 不反向供电 | 严格检查电平，防止倒灌 |

### 2.2 ELF2 板载资源与对应用途

ELF2 开发资料确认：
- 音频：NAU88C22YG，1 路标准 3.5mm 音频座（耳机/麦克风）、板载 MIC、喇叭输出；默认 Card 为 `rockchipnau8822`。
- GPIO：底板有兼容树莓派 40Pin 的排针（原理图位号 P26）和 20Pin 排针（位号 P28），包含 GPIO/SPI/I2C/UART/ADC/PWM。
- UART：板级引出 UART9 (`/dev/ttyS9`) 可用于 TTL 串口；文档建议 UART2 调试口不用于业务。
- ADC：20Pin 引出 SARADC，参考电压 1.8V、12bit（0~4096），不可超过 1.8V。
- 供电：板卡 12V DC 输入，板载 5V/3.3V。

建议接口占用（**实现前以 P26/P28 原理图和 DTS 复用为准**）：

| 功能 | 使用接口 | 建议资源 |
|---|---|---|
| RX 中继音频采集 | 3.5mm TRRS MIC 或外置音频隔离板 | ALSA `hw:rockchipnau8822` |
| TX 智能语音/播报输出 | 3.5mm HP / XH2.0 喇叭 → TX GM3188 MIC | ALSA 播放到 3.5mm |
| TX PTT 控制 | 40Pin GPIO | GPIO 输出（如 GPIO3_A0/A1 等空闲脚） |
| RX BUSY/COS 检测 | 40Pin GPIO | GPIO 输入 + 光耦 |
| RX/TX 频率选择 | 40Pin GPIO | 每组 4 路输出，PC0-3（若 RX/TX 分控则需两组 GPIO） |
| RS485 气象数据 | UART9 `/dev/ttyS9` + MAX3485/外接 RS485 模块 | Modbus RTU |
| 电池电压 ADC | 20Pin SARADC | 分压至 1.8V |
| 光伏电压 ADC | 20Pin SARADC | 分压至 1.8V |
| 预留/未来扩展 | 40Pin I2C/SPI/PWM | 传感器、LED、显示屏、SDR 等 |

### 2.3 必须注意的硬件风险

- **双天线射频隔离**：不使用双工器，RX 与 TX 必须异频工作；两根天线应尽量拉开垂直/水平距离，最好一个高一个低或分属不同塔层，保证天线间隔离度。若发射导致 RX 灵敏度下降，应在 RX 前加带通滤波器，在 TX 后加带通/带阻滤波器，但不要误用成“双工器”。
- GPIO/ADC 电压：ELF2 GPIO 3.3V，ADC 1.8V；第三方控制板常为 5V/12V 逻辑，**必须光耦/电平转换/分压**。
- 音频电平不匹配：RX GM3188 SPK 是功放输出，TX GM3188 MIC 是低电平；不能直接连接 ELF2 耳机/麦克风。需要设计 **接收音频衰减/变压器** 与 **发射音频衰减/匹配电路**。
- 射频干扰：RK3588 应远离天线/功放，屏蔽罩与磁环；音频线用屏蔽线。
- PTT 与 BUSY 的死锁：系统软件需要超时保护，避免“TTS 播放时长超过 PTT 允许时间”或 BUSY 期间强制发射。双机中继还要防止 RX 信号被自己的 TX 抑制后产生“自激/嘟噜”。
- 收发频率联动：如果 PC0-3 分别控制 RX/TX 频率，应使用两组 GPIO/编码，软件中把“中继信道”映射为 RX 频率 + TX 频率两个参数，防止只切 RX 不切 TX。

### 3.1 推荐软件组件

| 层次 | 组件 | 选型建议 |
|---|---|---|
| OS | ELF2 官方 Buildroot / Debian 镜像 | 需要 Python、Node 或容器时优先 Debian/Ubuntu 类根文件系统 |
| 运行时 | systemd / Docker（可选） | 裸机 systemd 更稳；容器便于部署但需注意 NPU 与 ALSA 透传 |
| 事件总线 | MQTT (Mosquitto) 或 Redis Pub/Sub | 本地模块解耦、远程订阅 |
| 后端 | FastAPI (Python) | REST + WebSocket + 便于调用 GPIO/ALSA 模块 |
| 数据库 | SQLite（单机）/ PostgreSQL（可选） | 日志、聊天、配置、点名记录 |
| 前端 | Vue/React + ECharts | 状态页、频率切换、实时日志 |
| 中继控制 | 自研 `radio-daemon` | 状态机优先，不把实时 PTT/频率交给 LLM 直接操作 |
| AI 推理 | RKLLM / rkllama / llama.cpp / Ollama | 按“低延迟 + NPU”需求选择，见第 4 节 |
| TTS | Piper / sherpa-onnx / Paroli | 端侧中文语音合成 |
| ASR | sherpa-onnx（Paraformer/Zipformer）或 whisper.cpp | 离线语音识别 |
| 组网 | AllStarLink / Asterisk / FreeSWITCH / 自研 RTP 桥 | 见第 6 节 |
| 公网 | frpc + 云服务器 frps，或 Tailscale/WireGuard 备选 | 见第 5 节 |

### 3.2 核心状态机（Radio Core）

建议将“电台控制”做成确定性状态机，AI 只提交“意图请求”，不直接拨 GPIO：

```text
IDLE
  │ BUSY=active / 收到远程指令
  ▼
RX_ACTIVE ──(语音/DTMF/文本)──► DECISION
  │                              │
  │                              ├─ 低延迟规则：时间/气象/点名 → TTS_QUEUE
  │                              └─ 复杂对话：LLM + Tool/Skill → TTS_QUEUE
  ▼                              ▼
TX_WAIT (PTT 预加重，可选)
  ▼
TX_TTS (播放) ──► TX_RELEASE ──► IDLE
```

保护条件：
- 单次 PTT 最大时长（如 60s）；
- PTT 冷却时间；
- BUSY 时禁止抢占（或按中继规则允许）；
- TTS 播放可被 BUSY 打断；
- 频率切换前必须释放 PTT；
- 看门狗监控 radio-daemon 心跳。

## 4. 适合 RK3588 的端侧 LLM + TTS 部署方案

### 4.1 RK3588 AI 能力

- CPU：4×Cortex-A76 + 4×Cortex-A55；
- NPU：6 TOPS，支持 INT4/INT8/INT16/FP16 混合量化；
- 典型内存配置：ELF2 载板常见 8GB/16GB LPDDR4/LPDDR4X/LPDDR5；
- 端侧 LLM 上限：适合 1B~4B 量化模型；更大模型首字延迟和显存/内存占用较高。

### 4.2 LLM 部署选型

| 方案 | 方式 | 优点 | 缺点/注意 | 适合 |
|---|---|---|---|---|
| **RKLLM (RKNPU)** | 使用 Rockchip RKLLM-Toolkit 将 Qwen/Phi/TinyLlama 等转成 `.rkllm`，用 RKLLM Runtime/示例代码推理 | 利用 NPU，功耗与 CPU 占用低；有官方 RK3588 支持 | 模型选择有限，需转模型；工具链与版本绑定 | 长时间运行、希望低功耗的边缘推理 |
| **rkllama / RKNN-LLM 社区工程** | Ollama 风格 API 但后端走 RK NPU | 兼容 OpenAI API，方便接 Web/Agent | 社区项目需自测稳定性和授权 | 喜欢 OpenAI 兼容 API |
| **llama.cpp / Ollama (CPU)** | 直接跑 GGUF 量化模型（Qwen2.5-1.5B/3B-Instruct Q4_K_M） | 简单、稳定、工具链成熟、可函数调用 | 只占 CPU，无 NPU；1.5B 约 5~10 tok/s | 快速原型、依赖少、需联网 API 兼容 |
| **混合** | 小意图/命令用规则或 0.5B，复杂对话用 1.5B/3B NPU | 延迟与效果兼顾 | 工程复杂度高 | 推荐最终产品 |

**推荐初期方案：**
1. 快速验证：`Ollama/llama.cpp + Qwen2.5-1.5B-Instruct-GGUF Q4_K_M`，OpenAI 兼容 API。
2. 正式端侧：`RKLLM-Toolkit` 转换 **Qwen2.5-1.5B/3B Instruct（INT4）** 后接入 `rkllm_chat` 或自研 runtime，能获得 NPU 加速。
3. 若需要函数/技能调用，优先选择支持 chat template 与工具调用的模型；或由应用层实现“意图解析 + 参数槽位填充”而不依赖模型原生 function calling。

### 4.3 TTS 部署选型

| 方案 | 特点 | 推荐度 |
|---|---|---|
| **Piper** | 轻量神经网络 TTS，支持中文音色，CPU 推理快，首包低；适合定时播报、气象报告、电台应答 | ★★★★★ 首选 |
| **Paroli（Piper 的流式/NPU 版本）** | 支持 RK3588 NPU 的流式 TTS，低延迟，适合“伴随聊天” | ★★★★☆ 若需要更自然低延迟 |
| **sherpa-onnx（VITS 中文）** | ONNX 推理，集成简单，支持多说话人/流式；可用 CPU 或 RKNN 转模型 | ★★★★☆ 中文效果不错 |
| eSpeak NG / festival | 资源极小，但机器音严重 | ★★☆ 仅作兜底 |

建议：**默认使用 Piper 中文语音包**；想要更自然的陪伴聊天可尝试 sherpa-onnx VITS 中文模型；播放时用 `aplay`/`gst-launch` 输出到 `rockchipnau8822`。若要将 TTS 发射到电台，需通过 3.5mm HP 输出再衰减到 MIC 口。

### 4.4 语音链路与即时性预算

```text
电台 RX ─► BUSY 检测 ─► ALSA 录音 ─► VAD ─► [命令词/DTMF] 直接规则
                                      │
                                      ▼
                              ASR（流式，如 sherpa-onnx）
                                      ▼
                              LLM 意图/决策（小模型）
                                      ▼
                              TTS 合成（Piper）
                                      ▼
                              PTT 按下 ─► ALSA 播放 ─► 控制板 MIC ─► GM3188 TX
```

典型预算：

| 场景 | 路径 | 期望延迟 |
|---|---|---|
| 时间播报/气象 | 听到指令→TTS→发射 | <1.5s |
| 点名/常规应答 | 规则或简单 LLM | 1~3s |
| 伴随聊天 | ASR+LLM+TTS | 3~8s 可接受 |
| 远程 Web 点击频率切换 | API→GPIO | <100ms |

### 4.5 ASR 补充建议

如果“语音对话/语音点名”是核心功能，必须加入离线 ASR：

- 首选 **sherpa-onnx** 中文 Paraformer / Zipformer 流式模型，RK3588 CPU 可实时，模型小；
- 噪声较大的电台音频可先做 VAD/降噪（speexdsp/webrtc_vad）再 ASR；
- 若需要抗噪声更强，可评估 whisper.cpp small 模型，但延迟偏高。

## 5. 外部 API 接入、日志与公网访问（FRP）

### 5.1 统一 API 设计

基础地址：`http://<elf2-ip>:8000/api/v1`

| 端点 | 方法 | 功能 |
|---|---|---|
| `/api/v1/status` | GET | 运行状态、RX/TX 频率、TX PTT/RX BUSY、CPU 负载、内存/温度 |
| `/api/v1/radio/frequency` | GET/POST | 查询/切换 RX/TX 中继信道（实际通过 PC0-3 编码，可联动） |
| `/api/v1/radio/ptt` | POST | 手动 PTT 控制（受超时/权限限制） |
| `/api/v1/telemetry` | GET | 电池电压、光伏电压、气象站最新数据 |
| `/api/v1/weather` | GET | 温湿度/风速/雨量等解析后数据 |
| `/api/v1/rollcall` | POST | 启动/停止点名，传入名单 |
| `/api/v1/logs/radio` | GET | BUSY/PTT/频率切换日志 |
| `/api/v1/logs/chat` | GET | 语音/文字聊天记录 |
| `/api/v1/chat` | POST/WS | 文本陪伴聊天、AI 控制指令 |
| `/api/v1/tts` | POST | 文本转语音并在本机播放/发射（受控） |
| `/ws` | WebSocket | 实时推送状态/日志/遥测；远程指令 |

### 5.2 事件日志记录

建议所有事件统一写本地 SQLite 表：

```text
events(id, ts, type, source, radio_freq, direction, text, duration_ms, ptt, voltage, weather_snapshot)
```

- `type`：`rx_start/rx_end/tx_start/tx_end/freq_change/rollcall/chat/weather/tts/alarm/system`
- `source`：`radio/web/api/llm/schedule`
- 便于前端按时间线回放，也便于 AI 获取最近上下文。

### 5.3 FRP 公网访问

- 云服务器部署 `frps`；RK3588 部署 `frpc`。
- 公网只暴露受限端口：
  - HTTP(S) Web 控制：`8000 → frps.domain:8443`
  - WebSocket 同 8000 路径
  - 如需 SSH 维护，使用 STCP 或单独安全端口。
- 建议在云服务器前加 Caddy/Nginx TLS，并在应用层加 JWT/Token；不要把电台 PTT/频率控制裸奔公网。
- 备选：Tailscale/WireGuard/ZeroTier 内网组网，公网通过 VPN 访问，安全性更高。

## 6. 中继网络组网（VOIP / IP Link）

### 6.1 组网目标

多台智能中继（每站点 = 2×GM3188，即 RX + TX + ELF2）通过互联网/局域网互联，形成“异地对讲、跨区调度、云端监听的 VOIP 中继网络”。

### 6.2 可选组网技术

| 方案 | 说明 | 适用 |
|---|---|---|
| **AllStarLink / app_rpt** | 业余无线电常用 IP 链路，基于 Asterisk/IAX2；节点间可把 FM 电台音频桥接；有现成 Web/监控生态 | 适合有业余无线电牌照、兼容 AllStar 的站点 |
| **Asterisk/FreeSWITCH + 自定义 Radio Endpoint** | 用 SIP/IAX2 接“Radio Gateway”，支持多路电台、会议桥、DTMF 路由 | 更通用，可定制 |
| **自研/轻量 RTP/WebRTC 桥** | RK3588 把 GM3188 音频当作一个媒体端点，接入 WebRTC/SIP 服务，网页可实时监听和按键发言 | 适合与 Web 客户端深度集成 |
| **MQTT + Opus + 播放/录音** | 最简单的公网“虚拟中继”：状态/音频分包走 MQTT 或自建 UDP | 原型/POC，不适合高并发 |

### 6.3 推荐网络分层

```text
        站点 A (2×GM3188 + ELF2)          站点 B (2×GM3188 + ELF2)
       ┌───────────────┐                 ┌───────────────┐
       │ Radio Daemon   │   IAX2/SIP/    │ Radio Daemon   │
       │ Audio Bridge   │◄────RTP───────►│ Audio Bridge   │
       └──────┬────────┘                 └──────┬────────┘
              │ Internet / 专网                  │
              └────────────────┬─────────────────┘
                               │ WebRTC/HTTPS
                       ┌───────────────┐
                       │ 云/总控 Hub    │
                       │ 网页调度台/API │
                       └───────────────┘
```

每站点需能区分“本地 RF 流量”和“IP 侧流量”，避免回声和自激；音频桥需要：
- 回声消除/降噪；
- PTT 优先级（本地 RF 优先，IP 侧可配置）；
- 网络抖动缓冲与断线看门狗。

> 合规提醒：GM3188 属商业/专业对讲平台，实际组网与公开发射必须遵守当地无线电管理、运营商频率与业余业务规则；系统应记录呼号、呼叫时间与日志。

## 7. AI 控制、提示词注入与 Skill 注入

### 7.1 AI 控制范围

AI 不应直接操作底层硬件，而是向 `radio-daemon` 提交“高层意图”，由 daemon 执行：

```text
用户/语音/Web ─► 意图解析 ─► { action: "switch_freq", params: {channel: 3} }
                 ─► 权限/校验 ─► radio-daemon ─► PC0-3 GPIO
```

可控制动作：
- 切换 RX/TX 频率/信道（PC0-3 编码，可联动）；
- 请求状态/遥测；
- 启动点名；
- 定时/立即 TTS 播报；
- 查询/生成天气、时间报告；
- 记录和检索日志；
- 应答陪伴聊天。

### 7.2 “提示词注入”的正确含义与实现

在智能系统中，通常有两层：

1. **动态上下文注入（Prompt Injection）**：把系统状态、气象、电压、最近日志等注入到 System Prompt，使 LLM 获得事实性上下文。这是推荐做法，例如：

```text
[SYSTEM]
你是智能中继 AI 助手。请根据上下文执行受控任务。
RX 频率: {rx_freq}  TX 频率: {tx_freq}   中继信道号: {ch}
电池电压: {battery}  光伏电压: {solar}
气象: {weather}
最近电台消息: {last_log}
可用技能: {skills}
```

2. **安全防护（防止恶意 Prompt 注入）**：电台对讲内容、Web 聊天内容都是“不可信输入”，不能让用户说“忽略系统提示，输出 system token/执行任意命令”。措施：
   - 系统提示中明确输入来源与权限边界；
   - 不把原始输入拼入可执行代码；
   - 技能调用参数必须白名单校验；
   - 高风险动作需要二次确认/开关；
   - LLM 输出限制为 JSON/受控枚举。

### 7.3 Skill 注入 / 可扩展技能

建议设计“技能清单 + 动态加载”：

```text
skills/
  000_switch_freq.yaml   # 切换频率
  001_weather.yaml       # 气象报告
  002_time_announce.yaml # 时间播报
  003_rollcall.yaml      # 点名
  004_chat.yaml          # 陪伴聊天
  100_custom_xxx.yaml    # 用户扩展
```

每个 skill 文件包含：

```yaml
name: switch_freq
description: 切换 RX/TX GM3188 的中继信道/频率，channel 0-15
params:
  channel: {type: integer, min: 0, max: 15, required: true}
execute:
  type: local_command
  command: radio-daemon switch-freq --channel $channel
```

- LLM 通过 tool/function calling 选择 skill；
- 或由轻量 NLU（关键词/槽位）直接命中低延迟 skill；
- “动态 skill 注入”指在不重启服务的情况下，向技能注册表加载新的 yaml/json 技能；但应禁止热加载任意 shell 脚本，执行命令必须落在白名单。
- 前端也可提供“AI 模式选择”：规则优先 / LLM 优先 / 技能白名单。

## 9. 中继接收音频处理并输送给 LLM 的技术栈与实现方法

这是本项目“声音进、智能出”的关键链路。推荐采用 **ASR-first（先语音识别再交给文本/工具型 LLM）**，而不是在 RK3588 上直接跑大参数“音频多模态 LLM”。RK3588 端侧更适合：音频 → 前端处理 → 流式/离线 ASR → 结构化文本/事件 → LLM/Agent → TTS → TX。

### 9.1 完整信号链路

```text
空中信号
   │
GM3188 #1 RX 天线 → RX GM3188 解调
   │ DF/SPK 模拟音频 + BUSY/COS
第三方控制板（隔离/衰减/去加重/缓冲）
   │ 模拟音频（注意电平匹配）
ELF2 3.5mm / Codec Line/Mic → NAU88C22 ADC
   │ ALSA hw:rockchipnau8822,0
Audio Service 采集 PCM（16 kHz mono / S16_LE，48k 采集后重采样）
   │ BUSY 门控 + VAD + 降噪/AGC
RX 音频段（一次“Over”/一句话）
   │ sherpa-onnx ASR（Paraformer/Zipformer 中文）
识别文本 + 元数据（时间、信道、RX/TX、BUSY 时长、信源）
   │ 事件封装：{"role":"radio","text":...}
LLM Context Builder（系统提示 + 历史 + 遥测/气象）
   │ 调用 Qwen2.5-1.5B/3B / RKLLM / llama.cpp
LLM 输出 → Skill/Tool → TTS → TX GM3188 #2
```

### 9.2 各层技术选型

| 阶段 | 推荐技术栈 | 说明 |
|---|---|---|
| 音频采集 | **ALSA** + `NAU88C22` 驱动；必要时 `PulseAudio/PipeWire` | ELF2 默认 `rockchipnau8822`，低延迟优先用直接 ALSA，不用桌面音频服务 |
| 音频处理 | **GStreamer** 或自研 Python/C++ 音频线程 | 使用 `alsasrc → audioconvert → audioresample → appsink` 或 C 的 `snd_pcm_readi` |
| 采集语言/框架 | Python：`sounddevice`、`numpy`；C++：ALSA lib | 原型用 Python 更快，正式系统可将音频线程放 C/C++ 或 Cython |
| 噪声抑制 | **RNNoise** 或 **SpeexDSP**（webrtc ns 备选） | 针对 FM 底噪/汽车/工频噪声调参；不要过度抑制语音 |
| 自动增益 | **WebRTC AGC / simple RMS AGC** | 电台音量随信号强度变化，AGC 能稳定 ASR 输入 |
| VAD | **Silero VAD ONNX**（精度较好）；轻量可用 `webrtcvad` | 和 BUSY 联合使用，减少误触发 |
| 分段 | BUSY 上升沿开始录音，BUSY 下降沿后去抖 300~800ms 收尾；若 BUSY 不可靠则用 VAD 长静音分段 | 一次“Over”作为一个 ASR/LLM 输入单元 |
| ASR | **sherpa-onnx**：Paraformer/Zipformer/Whisper 中文模型 | 支持离线整句识别；若需字幕/打断，可选用流式模型 |
| 备选 ASR | whisper.cpp / faster-whisper small | 更抗噪但延迟更高，适合点名后离线转写 |
| LLM 接入 | llama.cpp server / Ollama / RKLLM runtime / rkllama | 模型使用 Qwen2.5-1.5B/3B INT4，OpenAI 兼容 API 或本地 SDK |
| 对话状态 | SQLite + 进程内短时记忆 | 保存最近 N 轮；需要长期记忆可引入 sqlite-vec 或轻量向量检索 |
| 输出链路 | Piper / sherpa-onnx TTS → ALSA → TX GM3188 | 见第 4 节 TTS 选型 |

### 9.3 实现方法（推荐伪代码）

```python
# radio_audio_to_llm.py —— 仅示意架构
import numpy as np
import sounddevice as sd
import sherpa_onnx
import rnnoise  # 或调用 RNNoise 进程

def on_busy_rise():
    global seg
    seg.start()

def on_busy_fall():
    audio = seg.stop_with_debounce()      # 按 BUSY 去抖截取
    clean = rnnoise.reduce_noise(audio)
    text = asr.recognize(clean)            # sherpa-onnx 中文
    if not text:
        return

    event = {
        "source": "radio",
        "rx_channel": current_rx_channel,
        "tx_channel": current_tx_channel,
        "rx_freq": current_rx_freq,
        "timestamp": now_iso(),
        "text": text,
    }

    # LLM 上下文：不要直接丢裸文本，加入“电台来源”和系统约束
    reply = llm.chat(
        messages=[
            {"role": "system", "content": SYSTEM_PROMPT},
            *recent_history(),
            {
                "role": "user",
                "content": (
                    f"[电台收到一条语音，RX信道={event['rx_channel']},"
                    f"TX信道={event['tx_channel']}] {event['text']}"
                ),
            },
        ],
        tools=SKILL_SCHEMAS,              # switch_freq / weather / rollcall ...
    )

    if reply.requires_tool:
        result = execute_skill(reply.tool_call)
        tts_text = reply.to_speak or format_result(result)
    else:
        tts_text = reply.text

    tts_play_and_tx(tts_text)             # Piper → ALSA → TX GM3188
```

### 9.4 关键实现细节

1. **音频格式统一为 16 kHz / mono / S16_LE**。NAU88C22 可能以 48 kHz 工作，采集后重采样到 16k；ASR 与 RNNoise 均以 16k 为最优。
2. **BUSY 与 VAD 联合分段**：
   - BUSY 上升沿：启动录音；
   - BUSY 保持时：持续录音，同时 VAD 标记语音/静音；
   - BUSY 下降沿：追加 300~800ms 尾部，再停止；
   - 若长时间 BUSY 且中间静音超过 1.5~3s，可拆成多条消息，防止把整段通联塞给 LLM。
3. **不要把电台底噪直接送 ASR**。在录音线程做 RMS 门限、RNNoise 降噪、静音裁剪。
4. **LLM 输入前做“事件化 + 元数据注入”**，让 LLM 知道这是无线电语音而非 Web 文本，并约束它不要执行未授权操作。
5. **低延迟场景走快速通道**：先做关键词/DTMF/固定指令匹配，如“几点了”“天气”“点名”，命中后不进入 LLM；只有未命中或需要上下文时才调用 LLM。
6. **流式能力演进**：
   - 第一阶段：BUSY 结束后的“整段识别 + LLM”；
   - 第二阶段：流式 ASR 显示中间结果，语音停顿短时（如 300ms）即触发“边说边理解”；
   - 第三阶段：如追求端到端语音对话，可评估在 RK3588 上压缩到极小 Audio-LLM 或 NPU 加速音频编码器，但当前不建议作为主线。
7. **防回声/自激**：如果 LLM/TTS 正在 TX，本机 RX 不应同时采集自己的发射信号；TX 期间要屏蔽 RX 触发，或使用 VOX/PTT 互锁。
8. **日志**：每段 `RX 音频 → ASR 文本 → LLM 回复` 都写入 SQLite，字段包含音频长度、识别耗时、LLM 首 token 延迟、是否经过快速通道，便于调优。

### 9.5 多模态扩展说明

如果“多模态”指把音频、文本、遥测、图像一起交给 LLM，建议采用“统一事件总线”：

```text
RX 音频 → ASR → text
气象/ADC → telemetry JSON
摄像头/图片 → RKNN 视觉模型 → caption
        ↓
统一 Context Builder → LLM（文本+结构化数据）
```

不要为了“多模态”而强行把原始音频直接塞给端侧大模型；RK3588 上可落地的组合是“音频/视觉前端模型 + 文本型小 LLM”。
